# AIME 预算实验

入口：`python -m Agent.cli.evaluate_budget_experiment`。不传 `--limit` 时评测全部 AIME 样本。

## v1

使用原 harness 的独立副本 `qwen_harness_v1.py`。累计 `total_tokens` 达到
`max_total_tokens` 的 50% 时发出第一次预算提示，80% 时发出第二次提示。
若 80% 时已有证据机制认可的候选答案，提前进入原有 finalization；
否则继续尝试解决最关键的未验证点，不强制猜答案。
事件名为 `budget_warning_v1`。

## v2

在 v1 基础上，每次数学工具返回后更新本次样本的工作记忆：原题文本、
显式候选答案、最近四条工具证据、候选可信状态及未验证点。
最终回合从这份记忆和证据记录构造输入，以减少历史文本。
工作记忆是记录和提示，不代表数学证明。事件名为 `working_memory_v2`。

各版本使用不同的 run 名称，方便与原始 run 对照。当前实现不会改动
`qwen_harness.py`、`math_workflow.py` 或原始 AIME 配置。

## v3

结合 v1 的 50%/80% 预算提示与 v2 的逐次工具结果记忆。已有可复核候选时，
沿用 v2 的紧凑最终输入；尚无可复核候选时，将工作记忆与最近的完整推理和
工具往返一同交给最终回合，输入估算上限为 12000 token，避免 v2 在无候选时
过早丢掉推理链。`finalization_context.working_memory_v3` 会标记这一分支。
这仍是实验性折中，是否提升准确率需要独立全量评测确认。

## v4

从原版 `qwen_harness.py` 独立复制运行逻辑，仅改变最终回合的单次输出
上限。`_final_output_budget_v4` 根据模型单次上限、剩余总 token 和实际
输入估算计算上限；不再把 `finalization.max_tokens: 2048` 当作最终输出
硬上限。原配置的 2048 仍用于普通求解阶段的保留预算和最终输入裁剪。
候选识别、收尾触发、工具和计划逻辑与 baseharness 相同。

## v5

在 v4 的动态最终输出上限上加入 v1 的累计 token 50% 与 80% 预警。
80% 时若已有证据机制认可的候选答案，会提前进入最终回合。事件名为
`budget_warning_v5`。本版本不加入 working memory。

## v6

在 v4 的动态最终输出上限上加入 v2 的工具结果 working memory。
每次数学工具返回后更新题目文本、候选答案、最近四条工具证据和未验证点；
最终回合以这份记忆构造紧凑输入。事件名为 `working_memory_v6`。
本版本不加入 50%/80% 预警。

## v7

从 v4 的动态最终输出上限出发，加入工具结果 working memory。已有候选时
使用紧凑 memory；`candidate_answer=None` 时，附带与最近未验证工具结果
相关的最近一到两组完整助手推理与工具结果。历史输入上限为 8000 token；
若完整组放不下，就减少组数，不截取选中组的推理段落。事件名为
`working_memory_v7`，最终上下文记录 `complete_recent_groups_v7`。

## v8

从 v4 出发，单独记录模型推导状态：当前方法、最近的等式或计算事实、
未验证点及模型明确写出的候选答案。每次模型文本响应后更新，并在最终
回合附带这个有界状态；记录标记为 `model_claims_unverified`，不视为工具
验证。事件名为 `reasoning_state_v8`。不引入 v7 的工具结果 memory。

## v9

以 v8 为基础，保留模型推导状态记录，并加入 v7 的工具结果 working memory。
最终回合在无候选答案时保留与近期未验证点相关的一到两组完整推理和工具
结果；有候选答案时使用紧凑 memory。分别记录 `reasoning_state_v9`、
`working_memory_v9` 事件，最终上下文记录 `complete_recent_groups_v9`。

## v10

以 v8 为基础。每次数学工具调用的 schema 要求写明 `counted_object`（计数对象，
非计数题则为目标量）和 `original_constraints`（相关原题条件）。缺失时拒绝
执行并返回可修正的工具错误；运行器将这两项记录在 `pretool_model_v10` 事件中，
底层工具只接收原有参数。该检查保证记录存在，不能自动证明数学模型正确。

## v11

以 v8 为基础。要求模型在最终 `####` 答案之前，用一行
`Counterexample check:` 指出一个针对当前方法的可能漏例、边界情况或条件
冲突，并根据原题和已有证据检查。最终回合再次明确该要求，仍禁用工具。
`counterexample_check_v11` 事件记录是否输出了检查行及其文本；这属于模型
自检，不能代替独立证明，也不额外增加模型回合。

## v12

以 v8 为基础。当 Python 工具要用推导出的公式计数时，调用需标记
`calculation_kind=formula_count`，并提供一个小实例及两段独立代码：直接
穷举与代入公式。运行器在隔离的 Python 进程中分别执行，要求两者各输出
一个相同的精确数值，才执行正式计算。缺失、执行失败或结果不一致时，
返回可修正的工具错误。其余 Python 计算标记 `other`，沿用 v8 的执行逻辑；
`exact_calculate` 不变。事件 `small_case_cross_check_v12` 记录适用性与结果。
该检查只验证模型选定的小实例，不保证公式覆盖原题的全部情况。

## v13

以 v8 为基础，加入每题独立的原题条件与证据对应表。初始表只引用原题的
原文片段和目标，不允许后续工具结果改写它们。每次数学工具返回后，更新
最近两条工具代码与输出摘要、失败状态和候选冲突；成功执行的工具结果仍标记
为“未机械验证条件覆盖”。每个非最终模型请求临时附上这份简短对应表，
不把重复副本追加到历史；最终回合把对应表与 v8 推导状态一起保护。
事件名为 `constraint_memory_initialized_v13`、`constraint_memory_updated_v13`，
最终输出元数据包含 `constraint_memory_v13`。本版本不引入 v10 的调用字段
门槛、v11 的反例提示或 v12 的小规模交叉核对。

## v14

从 v8 独立复制。仅在数学工具失败（包括断言失败）或出现多个不同候选答案时，
生成简短异常记忆；下一次模型请求只提示一次，随后清除。正常成功结果
不会进入记忆，也没有每轮重复的表。最终回合若仍有未送达的异常，会将其
纳入受保护状态。事件名 `anomaly_memory_v14`、
`anomaly_memory_delivered_v14`。

## v15

从 v8 独立复制。每条数学工具结果带调用 ID 和状态：`current`、`failed`、
`superseded` 或 `disputed`。失败后的成功修正，以及模型明确称修正代码且
代码不同后的成功结果，会使旧记录失效；不同工具候选会登记冲突。
最终回合过滤已失效的工具结果与对应候选，并保留未解决候选冲突。
运行时的完整历史仍由 v8 保存。事件名 `evidence_version_v15`。

## v16

从 v8 独立复制。v8 在当前 90 题中未触发上下文压缩，因此 v16 单独设置
工作上下文的 6000 token 触发阈值与 4500 token 目标（不改变模型的
context window 或总 token 预算）。只在触发压缩时生成检查点：带来源
调用 ID 的已通过代码断言的计算、窄条件下可提取的候选，以及模型声明的
下一未验证点。检查点不视为数学证明；旧历史由现有压缩器处理，原题与
最近消息保留。事件名 `checkpoint_created_v16`。
